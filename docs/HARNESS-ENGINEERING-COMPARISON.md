# DeadReckon and harness engineering

This table compares DeadReckon with the concepts in Birgitta Böckeler's
[Harness engineering for coding agent users](https://martinfowler.com/articles/harness-engineering.html#FeedforwardAndFeedback).

    | Article concept | In DeadReckon | How |
    |---|---|---|
    | Outer user harness | Fully baked in | DeadReckon wraps existing coding-agent CLIs and owns their execution boundary, verification and promotion. |
    | Feedforward guides | Fully baked in | Every worker prompt receives the goal, acceptance criteria, selected skill and previous feedback. See [`turn_loop.rs`](../crates/deadreckon-runtime/src/turn_loop.rs#L2795) and [`default-coding/SKILL.md`](../skills/default-coding/SKILL.md#L15). |
    | Guide/sensor coherence | Particularly strong | Before execution, DeadReckon freezes the goal, contract, policy and source identity and binds them by digest. The exact contract shown to the worker is later evaluated by the gate. See [`job.rs`](../crates/deadreckon/src/commands/job.rs#L223). |
    | Computational feedback sensor | Fully baked in | `dr-gate` deterministically executes the approved checks, validates tamper evidence and only then signs the result. See [`gate.rs`](../crates/deadreckon-core/src/gate.rs#L653). Default test contracts are detected across Rust, Node, Go, Python, JVM and other ecosystems in [`acceptance_defaults.rs`](../crates/deadreckon-core/src/acceptance_defaults.rs#L80). |
    | Inferential feedback sensor | Fully baked in | A fresh, read-only model receives the goal, contract, diff, deterministic marker, authority and implementation notes. It must return `achieved`, `revise` or `uncertain`. See the evidence pack and judge prompt in [`semantic_judge.rs`](../crates/deadreckon-runtime/src/semantic_judge.rs#L189). |
    | Closed self-correction loop | Fully baked in for Single Jobs | A gate failure is appended to the history and execution continues with another worker turn. See [`turn_loop.rs`](../crates/deadreckon-runtime/src/turn_loop.rs#L5777). A semantic `revise` similarly feeds its summary and missing requirements into the next turn. |
    | Fail-closed human boundary | Fully baked in | An uncertain or unavailable judge becomes `NEEDS_REVIEW`; it cannot silently promote. The human still defines or approves “done” and chooses whether to apply the verified result. |
    | Steering the harness from repeated failures | Present but experimental | `learn index` extracts repeated failures, acceptance gaps, slow paths and other signals; `learn propose` turns them into cited proposals; `improve self` evaluates an isolated candidate. See [`AS-BUILT-ARCHITECTURE.md`](AS-BUILT-ARCHITECTURE.md#L2549). The project currently labels this capability experimental and potentially removable in [`MAP-OF-DEADRECKON.md`](MAP-OF-DEADRECKON.md#L198). |
    | Keep quality left | Partial | The contract exists before the first turn and checks run before promotion, but sensors generally run at a completion boundary—not continuously after each edit or tool call. |
    | Maintainability, architecture and behaviour harnesses | Infrastructure exists; policy is mostly user-supplied | DeadReckon provides tests, file/content checks, builds and arbitrary shell checks. It does not inherently know a project's architectural boundaries, performance requirements, mutation-testing policy or product behaviour unless those are encoded in its acceptance contract. |
    | Continuous drift/runtime sensing | Not currently inherent | DeadReckon monitors its own job lifecycle, processes, spend and containment, but it does not continuously monitor deployed SLOs, dependency drift, dead code or production behaviour and automatically start corrective work. |
    | Harness templates | Partial | Detected default contracts, acceptance packs and reusable skills resemble pieces of a template, but there is no first-class bundled “service topology + guides + sensors” abstraction of the kind described in the article. |
