Implementation notes

Design decisions

  • implementation-notes.html is the executor-maintained working file, while RUN-DECISIONS.md remains the published Markdown ledger for reviewers and library copies.
  • The runtime seeds the notes file at the working-directory root and renders its four required sections into every templated or polished decisions document.
  • The completion gate uses the existing turn-document journal to prove the notes file was updated no earlier than the latest documentable implementation change, avoiding any pipeline state schema change.
  • CLI-subagent and JSON-action providers share the same notes contract, but JSON-action fixtures usually need a separate notes-writing turn before done.

Deviations

  • No new public doc kind was added. The existing deadreckon doc <id> --kind decisions path is the review surface for the converged ledger.
  • Lifecycle tests opt into --no-docs for mock runs so they verify templated ledger behavior without invoking a real local documentation LLM.

Tradeoffs

  • Using HTML for the working notes preserves the requested filename and makes section extraction straightforward, at the cost of requiring stable section IDs.
  • Freshness is turn-based rather than content-diff semantic analysis. It catches stale or missing notes reliably without deciding whether the prose is good enough.
  • Polished narrator output can enrich decisions, but the write path preserves the converged ledger shape if a legacy or partial polish response omits the required sections.

Open questions

  • Should future runs expose a first-class --kind implementation-notes doc view, or is keeping decisions as the single public ledger enough?
  • Should the freshness gate eventually require non-placeholder text in each section, beyond section presence and turn recency?
